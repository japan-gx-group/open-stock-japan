# システム監査への対応

OpenStock Japan が、システム監査（IT 全般統制の評価、内部監査、個人情報の安全管理措置の点検など）で問われる点に、どう対応しているかをまとめます。

読む人は、このツールを運用する会社の管理者と、監査を行う人（監査役・内部監査・外部の監査人）を想定しています。

このツールだけで監査に通るわけではありません。ツールが担う部分と、運用する会社が担う部分があります。この文書は、その境目をはっきりさせるためのものです。

## 1. 全体像

| 監査で問われること | ツールが備えていること | 運用する会社が行うこと |
|---|---|---|
| だれが使えるか（アクセス管理） | 5 つのロール、権限の判定はすべてサーバ側、株主は自分の情報だけ | ロールを必要な人だけに付ける。退職・異動のときに外す。定期的に棚卸しをする（[4.4](#44-アカウントの棚卸し)） |
| 本人であることの確認（認証） | パスワードの決まり、二要素認証、ログイン失敗の記録とロック、セッションの期限 | 二要素認証を必須にする。Supabase 側の認証の設定を合わせる（[5.1](#51-supabase-の設定)） |
| だれが・いつ・何をしたか（監査証跡） | すべてのデータの変更を、変更前後の値つきで自動で記録。ログイン・出力・権限エラーも記録 | 監査ログを定期的に確かめる。検査の結果を控える（[5.3](#53-定期的に行うこと)） |
| 記録を書き換えられないか（証跡の完全性） | 監査ログは追記専用。ハッシュの連鎖で、書き換え・抜き取りを検出 | DB に直接つなげる人を絞る。最新の連番とハッシュを別の場所に控える |
| データが正しいか（完全性） | 入力の検証、DB の制約、台帳の整合の点検、変更の履歴 | 登記事項証明書・定款・契約書と照らして確かめる |
| プログラムの変更が管理されているか（変更管理） | マイグレーションは追記のみ・DDL 専用（機械チェック）、テスト、CI | 本番への反映の手順と承認を決める。反映の記録を残す |
| 止まったとき・消えたときに戻せるか（運用） | 死活確認の API、構造化されたログ | バックアップと復元の手順を決め、復元を試す（[5.2](#52-バックアップ)） |
| 外へ出ていく情報（外部送信） | AI へ送る前の確認と送信の記録、共有リンクの期限・取り消し・アクセスの記録 | AI の提供元との契約・設定を確かめる。共有リンクを必要な範囲に絞る |

## 2. ロールと権限

| ロール | できること |
|---|---|
| 管理者 | すべての操作。組織の設定、メンバーと株主の招待、ロールの変更、AI の設定、監査ログの閲覧 |
| メンバー | 業務データ（株主・株式・会議・決算・文書）の閲覧と編集 |
| 閲覧のみ | 業務データの閲覧 |
| 監査人 | 業務データの閲覧と、監査ログ・アカウントの棚卸しの閲覧。何も変えられない |
| 株主 | 株主ポータル（`/external-portal`）だけ。自分の保有状況と、公開されたお知らせ・決算・文書 |

- **監査人ロール**は、監査を行う人に「見られるが変えられない」権限を渡すためのものです。管理者の権限を渡さずに、監査ログまで確かめてもらえます。
- 権限の判定は、必ずサーバで行います（`src/lib/authz.ts`）。画面の出し分けは見た目だけで、判定には使いません。
- 業務データのテーブルは、ブラウザから直接は読めません。サーバが権限を確かめてから返します（[architecture.md](architecture.md)）。
- 管理者が 1 人もいなくなる変更は、DB のトリガーが止めます。
- 権限の無い操作を試みると拒否され、その事実が監査ログに残ります（`access.denied`）。

このツールには、「登録する人」と「承認する人」を分ける承認の流れはありません（[7. 限界](#7-このツールだけでは担保できないこと)）。

## 3. 監査ログ

### 3.1 何が残るか

監査ログ（`system_audit_logs`）には、3 つの経路で記録が入ります。

| 記録元 | 残るもの | 残し方 |
|---|---|---|
| データの変更（`db`） | すべての業務・設定のテーブルの、行の追加・更新・削除。変更前と変更後の値つき | DB のトリガー。データの変更と同じトランザクションで残るので、アプリのコードの書き忘れで抜けることがありません |
| 認証（`auth`） | ログイン（接続元の IP アドレスとブラウザつき）、ログアウト、パスワードの再設定の要求、二要素認証の登録・解除など | 認証サービス（Supabase Auth）のテーブルに付けたトリガー |
| アプリの操作（`app`） | 行の変更だけでは分からない操作（下の表） | サーバが記録 |

アプリの操作として残るもの:

| 操作 | 記録の名前 |
|---|---|
| ログインの失敗、失敗が続いたときのロック | `auth.login.failed` / `auth.login.locked` |
| 二要素認証の登録、コードの誤りとロック、管理者による解除 | `auth.mfa.enroll` / `auth.mfa.verify.failed` / `auth.mfa.locked` / `auth.mfa.reset` |
| パスワードの変更・再設定 | `auth.password.change` / `auth.password.reset` |
| 本人確認（操作の前の、パスワードの再入力）の失敗とロック | `auth.reauth.failed` / `auth.reauth.locked` |
| 権限の無い操作の試み | `access.denied` |
| 文書のダウンロード | `documents.download` |
| 共有リンクからのアクセス（ログインしていない人） | `share_links.access` |
| 株主名簿・資本政策表・新株予約権原簿の Excel への出力、議事録の印刷 | `export.*` / `print.*` |
| 監査ログの閲覧・CSV 出力・改ざんの検査、アカウントの棚卸しの出力 | `audit_log.view` / `audit_log.export` / `audit_log.verify` / `access_review.export` |
| AI への送信（提供元・モデル・送ったものの種類と量。内容そのものは残さない） | `ai.request` |
| 文書テンプレートから文書を作った（どのテンプレートで、どの会議・回次を対象に。文面は残さない） | `document-templates.compose` |
| 招待の発行・取り消し・受諾、メンバーのロールの変更・削除、退会 | `invite.*` / `member.*` / `account.delete` |
| 株主ポータルへの招待・取り消し | `portal_access.*` |
| 株式譲渡・株式分割などの、まとめての記録 | `equity.*` |

### 3.2 1 件の記録に入るもの

| 項目 | 内容 |
|---|---|
| 連番 | 組織ごとに 1 から。DB が振ります |
| 日時 | DB サーバーの時刻。呼び出し側が渡した時刻は使いません |
| 操作した人 | アカウントの id と、その時点のメールアドレス・ロール。あとでアカウントが消えても、だれだったかが残ります |
| 操作・対象 | 何をしたか、どのテーブルのどの行か |
| 変更前・変更後の値 | 追加は行の全体、削除は消えた行の全体、更新は変わった項目だけ |
| 結果 | 成功・失敗・拒否 |
| 接続元 | IP アドレス、ブラウザ、リクエストの番号（同じ操作から生まれた記録は、同じ番号でたどれます）。IP アドレスは、アプリの前に置いたプロキシが付けた値です（[5.4](#54-動かす環境)） |
| ハッシュ | この記録と、直前の記録のハッシュから計算した値（[3.3](#33-書き換えられないこと)） |

残さないもの:

- パスワード、二要素認証の秘密の値、招待・共有リンクのトークン、AI の API キー（暗号文も含めて「（秘匿）」に置き換えます）
- AI に送った内容と AI の出力
- 長い値（4,000 文字を超えるもの）。文字数とハッシュだけを残します

監査ログには、株主の氏名・住所など、変更前後の値として個人情報が入ります。読めるのは管理者と監査人だけです。

### 3.3 書き換えられないこと

- **追記専用**: 監査ログの更新・削除・全消去は、DB のトリガーが拒否します。アプリが使う権限（`service_role`）からも、更新・削除の権限を外しています。ブラウザからは読むことも書くこともできません。
- **ハッシュの連鎖**: 記録のたびに、「直前の記録のハッシュ + この記録の内容」から SHA-256 のハッシュを計算して残します。途中の記録を書き換えたり抜いたりすると、そこから先のハッシュが合わなくなります。
- **検査**: 監査ログの画面の「改ざんの検査」で、連鎖を先頭から計算し直して確かめられます。合わないときは、最初に合わなくなった連番と理由（連番の飛び・前の記録とのつながり・記録の内容）が分かります。
- **操作した人を偽れない**: 操作した人は、サーバがセッションを確かめて決めます。ブラウザが送ってきた値は使いません。すべてのリクエストがプロキシ（`src/proxy.ts`）を通り、そこで付けた印が合うときだけ、サーバは「だれの操作か」を受け取ります。

検査で分からないことが 1 つあります。**末尾の記録を消された場合**です。連鎖は途中の変更を見つけますが、いちばん新しい側が消えても、残りの連鎖は正しいままです。これを見つけるために、検査の画面に出る「最新の連番」と「最新のハッシュ」を、定期的に別の場所（月次の記録、監査人との共有フォルダなど）に控えてください。次に検査するとき、控えた連番とハッシュを「控えと照合する」の欄に入れると、その連番の記録がいまも残っていて、ハッシュが同じかどうかを確かめられます。同じであれば、そこまでは変わっていません。

### 3.4 見る・出す

監査ログの画面（サイドバーの「監査ログ」。管理者と監査人だけ）で、次のことができます。

- 期間・操作した人・操作の種類・結果で絞り込む
- 1 件ごとに、変更前と変更後の値を見比べる
- 同じ操作から生まれた記録をまとめて見る
- CSV に出力する（1 回に 50,000 件まで。出力したこと自体も記録されます）
- 改ざんの検査をする（控えておいた連番・ハッシュとの照合もできます）
- アカウントの棚卸しの一覧を見る・出力する

## 4. 認証とアクセスの管理

### 4.1 パスワード

- 12 文字以上で、英字と数字を両方含むこと。招待の受諾・初回登録・再設定・変更のすべてで、画面とサーバの両方が確かめます。
- パスワードの変更には、現在のパスワードが必要です。認証サービスを直接呼んでも、現在のパスワードなしには変えられません（`require_current_password`）。
- パスワードを忘れたときは、メールに届くリンクから再設定します。再設定できるのは、そのリンクを踏んで入ってきた直後（15 分以内）のセッションだけです。ログイン中のセッションを手に入れただけの人は、再設定の手順を使えません。
- パスワードの変更・二要素認証の解除・AI の API キーの登録の前には、パスワードをもう一度入力します。この入力の誤りも記録し、15 分のあいだに 5 回続くと 15 分止めます。
- メールアドレスの変更は、古いアドレスと新しいアドレスの両方で確認が済むまで反映されません。
- パスワードは、認証サービス（Supabase Auth）がハッシュ化して保存します。このツールは平文を保存しません。

### 4.2 二要素認証

- 認証アプリ（6 桁のコード）による二要素認証を、アカウントごとに設定できます（設定 ＞ アカウント。株主は、株主ポータルの上の「二要素認証」から）。
- 管理者は、社内のアカウント（管理者・メンバー・閲覧のみ・監査人）に二要素認証を必須にできます（設定 ＞ 組織・メンバー ＞ セキュリティ）。必須にすると、設定していない人は、設定が済むまでほかの画面を使えません。必須にできるのは、自分が二要素認証を設定済みの管理者だけです。
- 二要素認証を設定したアカウントは、コードを入力するまで、画面も API も使えません。判定はサーバと DB の両方で行います（ブラウザから DB を直接読もうとしても、コードを入力するまでは何も返りません）。
- コードの誤りは監査ログに残り、15 分のあいだに 5 回続くと、そのアカウントのコードの確認を一時的に止めます。
- 端末は 2 台まで登録できます（予備の端末）。回復コードはありません。端末を失くした人は、管理者がメンバー一覧から二要素認証を解除します（解除したことは監査ログに残ります）。
- 自分で解除するには、現在のパスワードが必要です。必須になっているアカウントは、最後の 1 台を解除できません。

**株主名簿には個人情報が入ります。社内のアカウントには、二要素認証を必須にすることを勧めます。**

### 4.3 ログインとセッション

- ログインの失敗は、試したメールアドレスと接続元つきで監査ログに残ります。
- 同じメールアドレスで失敗が続くと（15 分のあいだに 5 回）、そのメールアドレスでのログインを 15 分止めます。止めているあいだは、正しいパスワードでも入れません。本人は、パスワードを再設定すると、待たずに入り直せます。
- アカウントの無いメールアドレスでの失敗は、1 時間に 60 件までを監査ログに残し、超えた分はサーバのログにだけ残します（でたらめなメールアドレスを次々に試して、消せない記録を増やされないようにするため）。
- ログインのあとに進む先（`?next=`）は、このサイトの中のパスだけを受け付けます。外部のサイトを指す値は使いません。
- 別のサイトから、ログイン中の人のブラウザを使って操作させること（CSRF）を防ぐため、状態を変える API の呼び出しは、このサイト自身からのものだけを受け付けます。
- メールアドレスが登録されているかどうかは、応答からは分かりません（登録の無いメールアドレスでも、パスワードの誤りでも、同じ応答を返します）。
- セッションは、ログインから 24 時間、または操作が無いまま 8 時間で切れます。「ログイン状態を保持する」を外すと、ブラウザを閉じたときにも切れます。
- ログインに成功すると、接続元の IP アドレスとブラウザが監査ログに残ります。

### 4.4 アカウントの棚卸し

監査ログの画面の「アカウントの棚卸し」に、すべてのアカウント（株主ポータルのアカウントを含む）が、ロール・作成日・最後のログイン・二要素認証の有無つきで並びます。未受諾の招待も出ます。

定期的に（四半期に 1 回など）、次の点を確かめてください。

1. 退職した人・担当を外れた人のアカウントが残っていないか
2. ロールが、いまの仕事に必要な範囲に収まっているか（管理者が多すぎないか）
3. 長く使われていないアカウントが無いか
4. 株主でなくなった人の株主ポータルのアカウントが残っていないか
5. 二要素認証を設定していない社内のアカウントが無いか

確かめた結果は、CSV に出力して保存しておくと、見直しをした証跡になります。

## 5. 運用する会社が行うこと

### 5.1 Supabase の設定

認証の決まりの一部は、Supabase 側の設定です。ローカルの開発環境では `supabase/config.toml` に書いてあり、同じ値を本番のプロジェクトにも設定します（Supabase のダッシュボード、または `supabase config push`）。

| 設定 | 値 |
|---|---|
| パスワードの最小の長さ | 12 |
| パスワードに必要な文字 | 英字と数字（`letters_digits`） |
| 二要素認証（TOTP）の登録と検証 | 有効 |
| セッションの期限 | ログインから 24 時間 / 操作が無いまま 8 時間 |
| 自分でのサインアップ | 無効（招待だけ） |
| メールアドレスの確認（Confirm email） | 有効。メールアドレスの変更は、古いアドレスと新しいアドレスの両方で確認する（Secure email change） |
| パスワードの変更に現在のパスワードを求める | 有効（`require_current_password`） |
| リダイレクト先の URL | サイトの URL（Site URL）を、公開している URL にする。追加のリダイレクト先は、必要なものだけにする |
| メールのコード（OTP）の桁数と期限 | 10 桁・15 分（900 秒）。再設定メールには、リンクと同じ効き目の数字のコードも入ります。6 桁・1 時間のままだと、認証サービスを直接呼んで総当たりできます |
| 再設定メールの送信の間隔 | 60 秒以上 |
| 認証サービスの回数の制限 | 有効にし、利用者の IP アドレスごとに数えられるようにする（自前で動かす場合は、認証サービスの手前のプロキシが付けるヘッダを設定する） |

アプリ側では、次の 2 点を確かめます。

- `SUPABASE_SERVICE_ROLE_KEY` を設定する。ログイン中の人の確認（ロールと二要素認証の状態）に使うので、無いとすべての画面が使えません
- マイグレーションをすべて適用してから、アプリを入れ替える（`npx supabase db push`）

セッションの期限など、Supabase の契約プランによって使えない設定があります。使えない場合は、その分を運用（端末のロック、利用後のログアウト）で補い、監査の説明に含めてください。

あわせて、Supabase のプロジェクトそのものへのアクセスを守ります。

- ダッシュボードに入れる人を絞り、二要素認証を必須にする
- `service_role` キーと DB の接続文字列を、サーバの環境変数以外に置かない。漏れたと思ったらすぐに更新する
- DB に直接つなげる人を絞る（[7. 限界](#7-このツールだけでは担保できないこと)）

### 5.2 バックアップ

このツールは、バックアップを取りません。データは Supabase（Postgres と Storage）にあります。

- DB: Supabase のバックアップ（日次のバックアップ、または時点を指定した復元）を有効にする。自前で動かす場合は `pg_dump` などで定期的に取る
- 文書のファイル: Storage の `documents` バケットを、DB と同じ間隔で写す
- **復元を実際に試す**。取れているだけでは、戻せることの確認になりません
- 保存の期間は、会社の決まりと法令に合わせる。株主総会・取締役会の議事録は 10 年間の備え置きが求められます（会社法 318 条・371 条）

監査ログは DB の中にあるので、DB のバックアップに含まれます。

### 5.3 定期的に行うこと

| 間隔 | 行うこと |
|---|---|
| 毎月 | 監査ログの画面で改ざんの検査をし（前回の控えと照合する）、最新の連番とハッシュを別の場所に控える |
| 毎月 | 監査ログで、権限エラー（`access.denied`）とログインの失敗が増えていないかを見る |
| 四半期ごと | アカウントの棚卸し（[4.4](#44-アカウントの棚卸し)） |
| 人の出入りのつど | 退職・異動した人のアカウントを消す、ロールを変える |
| 年 1 回 | バックアップからの復元を試す |

### 5.4 動かす環境

- `APP_URL` に、公開している URL を設定する（招待リンクと、外部のサイトからの操作を弾く確認に使います）。実際の URL と違っていると、ログインが拒否されます
- **アプリを、プロキシ（ロードバランサ・CDN・リバースプロキシ）の後ろに置く。** 監査ログの接続元と、ログインの失敗の回数の制限は、`X-Forwarded-For` を右から数えた位置の値を使います。左側の値は利用者が自由に書けるので、信じません
- `TRUSTED_PROXY_HOPS` に、アプリの前にあるプロキシの段数を設定する（既定は 1。Vercel や nginx 1 台なら 1、CDN とロードバランサの 2 段なら 2）。段数が合っていないと、接続元として、利用者の申告した値やプロキシの IP アドレスが記録されます
- 最初の登録の前に `SETUP_TOKEN`（16 文字以上の乱数）を設定する。本番では、これが無いと初回の登録（`/signup`）を受け付けません。公開してから最初の登録までのあいだに、別の人が先に登録して管理者になるのを防ぐためです
- HTTPS で公開する（HTTPS のときは、ログインの Cookie に Secure 属性を付け、暗号化されていない通信には載せません）
- サーバのログ（標準出力の JSON）を集めて保存する。監査ログへの記録に失敗したときは、ここに残ります

## 6. 導入したときの確認

本番に入れたら、次の点を確かめてください。

1. **ログインが記録されるか。** ログインし直して、監査ログの画面に「ログイン」が、接続元つきで出ることを確かめます。出ない場合は、認証のテーブルにトリガーを作れていません。次の SQL で 2 行返るかを見ます。

   ```sql
   select c.relname, t.tgname
   from pg_trigger t
   join pg_class c on c.oid = t.tgrelid
   join pg_namespace n on n.oid = c.relnamespace
   where n.nspname = 'auth' and t.tgname like 'openstock_audit_%';
   ```

2. **データの変更が、操作した人つきで記録されるか。** 権利者を 1 件編集して、監査ログに「データの変更」が、自分の名前・変更前後の値つきで出ることを確かめます。操作した人が空の場合は、リクエストがプロキシ（`src/proxy.ts`）を通っていません。

3. **監査ログを書き換えられないか。** DB に `service_role` でつないで更新・削除を試し、拒否されることを確かめます。

   ```sql
   set role service_role;
   update system_audit_logs set detail = 'x' where seq = 1;  -- permission denied になること
   reset role;
   ```

4. **改ざんの検査が通るか。** 監査ログの画面で検査し、「問題なし」になることを確かめます。

5. **権限。** メンバー・閲覧のみ・株主のアカウントで、監査ログの画面が開けないことを確かめます。

## 7. このツールだけでは担保できないこと

監査の説明で、正直に伝える必要がある点です。

- **DB の管理者は、何でもできます。** DB に管理者としてつなげる人は、トリガーを外して監査ログを書き換えられます。ツールが防げるのは、アプリ経由の書き換えまでです。途中の書き換えは検査で見つかりますが、防ぐのは DB へのアクセスの管理です。
- **末尾の記録の削除は、検査だけでは見つかりません。** 最新の連番とハッシュを外に控えておく必要があります（[3.3](#33-書き換えられないこと)）。
- **画面で見たことは記録しません。** 記録するのは、変更・ダウンロード・出力・ログインです。「だれがどの株主の画面を開いたか」までは残りません。
- **画面のボタン以外の持ち出しは記録できません。** Excel への出力は、記録できたときだけ行います。ただし、データを読める権限を持つ人が、API の応答を自分で保存することまでは記録できません。
- **承認の流れはありません。** 登録した人と別の人が承認する、という仕組みは無いので、重要な登録（株式の異動、ロールの変更）は、あとから監査ログで確かめる運用になります。
- **ロックは、このツールのログイン画面を通る場合の決まりです。** 認証サービスを直接呼ばれた場合は、Supabase 側の回数の制限が働きますが、失敗の記録はこのツールの監査ログには残りません（Supabase 側のログに残ります）。
- **ロックは、いやがらせにも使えます。** メールアドレスを知っている人が、わざと失敗を繰り返すと、そのアカウントのログインを 15 分止められます。本人は、パスワードを再設定すれば待たずに入り直せます。管理者が手で解除する機能はありません。
- **メールを受け取れることが、最後のよりどころです。** パスワードの再設定は、メールのリンク（または同じメールのコード）で行います。メールのアカウントを乗っ取られると、パスワードを変えられます。社内のアカウントには二要素認証を必須にしてください（二要素認証は、パスワードを再設定しても外れません）。
- **接続元の IP アドレスは、プロキシの設定に依存します。** アプリをプロキシなしで公開した場合と、`TRUSTED_PROXY_HOPS` が実際の段数と合っていない場合は、当てになりません。また、ブラウザから DB を直接更新できる少数の項目（組織の基本情報・自分の氏名と電話番号）の記録では、接続元は参考値です。
- **ログインの Cookie は、ブラウザのスクリプトから読めます。** 認証の仕組み（Supabase のブラウザ用クライアント）の制約で、HttpOnly にできません。スクリプトの混入（XSS）への備えは、入力の扱いと CSP です。CSP は、いまは報告だけ（Report-Only）で、強制はしていません。
- **日時は DB サーバーの時刻です。** 時刻のずれの管理は、DB を動かす基盤に任せています。
- **バックアップ・基盤の監視・障害への対応は、運用する会社と Supabase の範囲です。**
- **このツール自体は、第三者の認証（ISMS、SOC 2 など）を受けていません。** 基盤の認証は、Supabase とホスティング先の報告書を確かめてください。
